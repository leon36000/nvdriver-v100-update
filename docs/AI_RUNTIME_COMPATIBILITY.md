# CUDA runtime and inference workload compatibility

**Review date:** 2026-11-02. The compatibility matrix below is **ANALYZED_STATICALLY**; a separate current-source llama.cpp build is **COMPILED_AND_STATIC_IMAGES_INSPECTED**. Neither is CUDA Driver API or hybrid-driver acceptance evidence.

The local project also contains a separate llama.cpp build from commit `1c5ed702c9e540ac14cc8c78100ea3984bc0e227` (0.8.0-dev), configured with CUDA Toolkit 12.9.2, NVCC 12.9.86, GCC 14.3.0, and CMake 4.4.5. Its verified CMake cache requests `70-virtual;120a-real`; `cuobjdump` 12.9.82 (SHA-256 `5a26d5abd391fb60e1d95f8d3d15d3467bd9515c496e187f1b1cbec225f67d9c`) found 146 SM70 PTX images and 146 SM120a cubins in `libggml-cuda.so.0.28.0`. The no-GPU verifier receipt is [`llama-cpp-cuda129-artifact-audit-v6-20261102.json`](../evidence/llama-cpp-cuda129-artifact-audit-v6-20261102.json); it pins the compiled `test-backend-ops` executable, captures CUDA Runtime/cuBLAS/cuBLASLt path, hash, size and file identity, and checks ELF dependency edges. The CLI `--version` smoke ran with `CUDA_VISIBLE_DEVICES` empty; no model was loaded and no inference or CUDA initialization was performed. This build proves compiler output and embedded image presence only; it does not prove that the SM70 PTX JITs, that either GPU executes this application, or that mixed-GPU execution works.

### Per-device ggml operation validation

The pinned source includes `tests/test-backend-ops.cpp`, a MIT-licensed test that compares supported ggml operation results on a selected backend against the CPU reference. Its CUDA target compiled in the same `GGML_CUDA=ON`, `CMAKE_CUDA_ARCHITECTURES=70-virtual;120a-real`, `GGML_BACKEND_DL=OFF`, P2P-disabled profile as the inference binary. The executable hash is `50e08c75955bd9c3d7084f1fdba7a665c0ebe0f9037db4fae21a2e3ec2e48981`; the artifact verifier recorded it in v5. It has not yet run on a GPU.

A software-only reproduction with `CUDA_VISIBLE_DEVICES` empty showed that upstream can return exit code 0 when `-b CUDA0` selects no enumerated backend: the program skipped its only CPU backend and still printed `1/1 backends passed`. The [sanitized reproduction receipt](../evidence/llama-backend-ops-no-device-v1-20261102T095447194680Z.json) and mode-0600 log preserve this result. The project wrapper [run_llama_backend_ops.py](../tools/run_llama_backend_ops.py) closes that false-success path. It requires a passing same-process hybrid acceptance receipt no older than 15 minutes, from authorized host `pc3` and the same kernel with identical CUDA visibility/order; it rejects `GGML_CUDA_DEVICES`, statically checks the pinned source's CUDA-index-to-PCI mapping, and matches each backend's reported GPU model. It hashes mapped libraries through a descriptor whose device/inode must match `/proc/<pid>/maps`, checks the test process's mapped `libcuda`, CUDA Runtime, cuBLAS, and cuBLASLt identities against the receipt/profile, then requires non-empty passing numerical comparisons. Cache reuse rechecks file identity and metadata on every poll; cached identities are rechecked after mappings disappear, and the aggregate requires one complete successful result for both SM70 and SM120. The two CUDA backends run separately. Expiry-before/between-backend, replacement, in-place changes before/during/after mapping, stubbed success, timeout, and host-restriction cases pass 35 focused tests; the full suite passes 2,503/2,503 in [receipt](../evidence/software-verification-llama-backend-ops-v3-20261102T1042Z.json). These are software-only checks. This qualifies no GPU operation: it does not validate llama.cpp inference, concurrent CUDA execution, production P2P, or hybrid-driver operation by itself.

After a successful same-process acceptance run on PC3, run the wrapper with that fresh receipt and exact PCI identities. The evidence directory must be new and below `evidence/`:

```sh
python3 -B tools/run_llama_backend_ops.py \
  --acceptance-receipt evidence/<fresh-hybrid-acceptance-receipt>.json \
  --expected-device '70=<V100-PCI-BDF>' \
  --expected-device '120=<RTX-5080-PCI-BDF>' \
  --evidence-dir evidence/llama-backend-ops/<new-run-id>
```

Run the CUDA probe and wrapper with the same `CUDA_VISIBLE_DEVICES` and `CUDA_DEVICE_ORDER`; the wrapper rejects changed settings and does not install or alter a driver module. Its default profile currently pins the local build artifact, so a separate target-host build needs its own matching profile and artifact hashes before this command can run there.

## First reproducible inference acceptance profile

The order matters: prove the CUDA Driver API and numerical kernels on both devices from one process first; then build/run an inference application. The profile below intentionally isolates layer placement from P2P:

1. Pin the llama.cpp commit above, CUDA Toolkit 12.8, CMake >=3.18, and a model file by source, license, and SHA-256. Do not download an unapproved model as part of a driver test.
2. Configure with GGML_CUDA=ON, GGML_NATIVE=OFF, and CMAKE_CUDA_ARCHITECTURES=70-virtual;120a-real. CUDA 13's llama.cpp automatic architecture list omits SM70; the explicit architecture pair is selected so Volta PTX and native Blackwell code are both built with the common CUDA 12.8 toolchain.

   Example configure/build commands after checking out the pinned source into an isolated directory:

       cmake -S "$LLAMA_SRC" -B "$LLAMA_BUILD" -DCUDAToolkit_ROOT="$CUDA_HOME" -DCMAKE_CUDA_COMPILER="$CUDA_HOME/bin/nvcc" -DGGML_CUDA=ON -DGGML_NATIVE=OFF '-DCMAKE_CUDA_ARCHITECTURES=70-virtual;120a-real' -DCMAKE_BUILD_TYPE=Release
       cmake --build "$LLAMA_BUILD" --target llama-cli --parallel

3. Use --list-devices to record device identities, then run one fixed GGUF model with --device CUDA0,CUDA1 --split-mode layer, an explicitly recorded tensor split, and flash attention off for the initial compatibility pass. Capture backend logs to verify that layers were assigned to both devices.

       llama-cli --list-devices
       llama-cli -m "$GGUF_PATH" --device CUDA0,CUDA1 --split-mode layer --tensor-split "$SPLIT" --flash-attn off -n 128 -p "$PROMPT"

4. Leave GGML_CUDA_P2P unset for the first run. Record outputs, token counts, prompt, context, quantization, split, and device logs. Compare with separate V100-only and RTX-only runs using the same model and settings.
5. Only after correctness is stable, enable GGML_CUDA_P2P in a separate run. First record cudaDeviceCanAccessPeer, PCI topology, IOMMU and NVLink status, and check integrity in both directions. A faster result is not required for correctness; any corruption/crash rejects the P2P path.
6. For any performance claim, pin clocks policy, temperature/power state, repetitions and exact input/model hashes; report TTFT, prompt-processing rate and generation tokens/s separately. No baseline gain has yet been measured.

The exact v0.8.0/CUDA 12.8 acceptance profile in this section has not been configured or compiled. Although the system `PATH` lacks CMake and the standard `/usr/local/cuda*` paths lack CUDA 12.8, project-local CMake 4.4.5 and a CUDA 12.9.2 toolchain were assembled and used for the separate current-source build above. Do not treat that different source revision/toolkit as the pinned v0.8.0 profile or as runtime evidence.

### Local SM120 compiler-header workaround — 2026-11-02

The system NVCC 13.1.115 accepts the installed GCC 15.2 host compiler according to NVIDIA's CUDA 13.1 compiler table, but an ordinary minimal SM120a `.cu` compile fails here because CUDA's `rsqrt`/`rsqrtf` declarations conflict with glibc 2.43 declarations in `bits/mathcalls.h`. Defining `_POSIX_C_SOURCE` did not change the failure. Adding `-U_GNU_SOURCE` to the NVCC command allowed a representative translation unit including `cuda_runtime.h`, `<cmath>`, and `<vector>` to compile with `-Wall -Wextra -Werror`; `cuobjdump --list-elf` confirmed two `sm_120a` cubins. This is a locally demonstrated compiler workaround, not a general CUDA/GCC/glibc fix.

The repeatable no-GPU check is [`verify_nvcc_cuda_smoke.py`](../tools/verify_nvcc_cuda_smoke.py); the passing [receipt](../evidence/cuda-toolchain-sm120-header-smoke-v3-20261102T0604Z.json) records successful version queries for NVCC, GCC and `cuobjdump`, plus the source, executable hash and cubin inventory. The helper never runs the executable or initializes CUDA. Restrict `-U_GNU_SOURCE` to CUDA translation units and re-evaluate GNU API dependencies when building a real application. It does not restore SM70 support in CUDA 13, nor replace the shared CUDA 12.8 build prerequisite for the selected V100+Blackwell inference workload. The first `-Wpedantic -Werror` smoke attempt also failed on NVCC-generated GCC line directives, so the maintained check uses `-Wall -Wextra -Werror` without `-Wpedantic`.

This distinction is consistent with NVIDIA's [CUDA 13.1 host-compiler support table](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-installation-guide-linux/index.html): the observed compiler is within the listed x86-64 GCC range, while the failure is in the local header interaction. The successful cubin inventory proves compilation and image presence only; no CUDA runtime or GPU was exercised.
