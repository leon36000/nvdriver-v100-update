# RM owns the architecture and class IDs consumed by UVM — 2026-11-03

R595 UVM receives its architecture and device-class selectors through the Resource Manager interface. In pinned R595.112.07 source, `uvm_gpu.c` requests `UvmGpuInfo`; `nvUvmInterfaceGetGpuInfo` forwards through `nv_uvm_interface.c` and `rm_gpu_ops_get_gpu_info` to `nvGpuOpsGetGpuInfo`. That RM path queries the GPU architecture/implementation and resolves classes such as host and CE. `uvm_hal_init_gpu` then performs exact lookups and fails with `NV_ERR_INVALID_CLASS` when a required row is missing. The stock R595 source lacks all six GV100 UVM HAL rows, while the isolated candidate restores them from the pinned R580 source.

This preserves the chosen boundary: the hybrid frontend routes each UVM request to the provider that owns that UUID, and the candidate UVM dispatches based on the selected provider's returned `UvmGpuInfo`. It must not invent or rewrite class values based on PCI IDs. The R580/R595 structure layout is statically equal, and CPU owner-routing contracts pass, but live RM values and hardware initialization are unverified.

REA/Ghidra also analyzed the exact project-built Dual MIT/GPL R595.112.07 UVM module, SHA-256 `7284d09d2f3ddafc24805ce9702d3bc596a3f2919468f79c5d9a9ac586f3cd48`. # Architecture decision record

## R580 module flavors split the target pair at Blackwell — 2026-11-01

The official [R580.196.07 kernel-module documentation](https://download.nvidia.com/XFree86/Linux-x86_64/580.196.07/README/kernel_open.html) states that the proprietary and open module flavors are mutually exclusive. The proprietary flavor supports Maxwell, Pascal, Volta, Turing, and later architectures until Blackwell; Blackwell requires the open flavor. The open flavor depends on GSP and does not support pre-Turing hardware. Consequently, an unmodified R580 install cannot use one kernel-module flavor to initialize both GV100 (Volta) and the RTX 5080 (Blackwell), even though both appear in broader product/API support information for the branch.

NVIDIA also says the user-space components are identical across the two R580 kernel-module flavors. That establishes same-release user-space parity, not cross-release R580/R595 `libcuda` and kernel ABI compatibility; the latter remains a separate static and hardware validation gate for this prototype.

The current source and lifecycle matrix makes the gap explicit: NVIDIA lists R580 as the last driver support for Volta, while its published R615.78.08 open-module source supports Turing and later. Blackwell requires the open flavor. NVIDIA's July 2024 blog also recommends proprietary modules for mixed older/newer deployments, but that general sentence sits alongside its Blackwell-open requirement and predates the current R615/Blackwell packaging rules; it cannot be applied as proof that an R580 proprietary stack initializes Blackwell. The chosen cross-release/provider experiment remains necessary to test whether a single user-facing CUDA stack can safely route to both providers.

Sources reviewed 2026-11-02: [NVIDIA CUDA/architecture support matrix](https://docs.nvidia.com/datacenter/tesla/drivers/cuda-toolkit-driver-and-architecture-matrix.html), [R615.78.08 open-module source README](https://github.com/NVIDIA/open-gpu-kernel-modules/tree/615.78.08), [NVIDIA module-flavor guidance from July 2024](https://developer.nvidia.com/blog/nvidia-transitions-fully-towards-open-source-gpu-kernel-modules/), and [current driver-installation updates](https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/latest/recent-updates.html). These establish support boundaries, not successful hybrid initialization.

**Selected experimental architecture:** a shared R595 frontend and Blackwell Open RM, a separately namespaced R580 proprietary GV100 provider, and one R595 UVM consumer with explicit provider ownership/isolation. This is the smallest existing code path that addresses the documented module-flavor split while preserving per-device CUDA contexts. It is not yet validated at runtime: current evidence is source/build/static closure, and PC3's last inventory had the V100 assigned to a VM while the RTX 5080 was host-visible. No single-process mixed-generation kernel result exists.

### Cross-provider P2P remains fail-closed

The pinned R595.99.02 UVM code creates its peer object in an RM session and explicitly requires both GPU objects to share that exact session in the capability and object-create paths. The hybrid bridge independently rejects mixed provider ownership before calling either backend; its capability response reports no link and its P2P object creation returns `NV_ERR_NOT_SUPPORTED` with a null handle. ABI conversion can translate the R580/R595 structure layout and link enum, but it cannot make a provider-local device handle or RM session valid in the other provider. This is the first concrete blocker to direct R580↔R595 UVM P2P, and relaxing the guard would be unsafe without a shared RM ownership model.

The source delta is now pinned at the producing ABI: R580's P2P caps structure is 64 bytes and R595 appends two `NvBool` fields, making it 72 bytes on x86-64. R580 also reports generic PCIe for its BAR1 path, while R595 has a distinct `PCIE_BAR1` link value. The existing adapter translates the old 64-byte payload and leaves the newer atomics false. These layout conversions preserve payload shape only; they do not bridge the provider-local session/handle ownership rule above. See the [source differential and compiled layout receipt](../evidence/r580-r595-p2p-abi-delta-v1-20261102.json).

The CPU-only composition regression covers both device orderings, the zeroed no-link response, rejection without backend fallback, and the R595 static-link discovery skip. A separate CUDA VMM probe can test whether explicit memory mapping and access permissions work across devices exposed through the common user API; even a numeric pass would not prove direct DMA, BAR1 mapping, or an R595 `NV50_P2P` object. See the [latest checkpoint](STATE.md) and [P2P test](../tests/test_hybrid580_uvm_p2p_bridge_contract.py). The exact v3 acceptance probe has now also passed its same-device SM120 numeric path on the stock PC3 RTX 5080, observed through a separate NVML pmon stream; this does not exercise the host-staged two-device fallback or change the fail-closed cross-provider P2P decision. See the [hardware receipt](../evidence/pc3-rtx5080-v3-pmon-runtime-summary-20261102.json).
The opt-in `--peer-transfer` probe now runs an independent host-staged fallback before the peer-capability query. For each direction it copies device memory to portable pinned host memory and then to the destination context, with separate synchronous and stream-ordered asynchronous numeric checks. These results are reported separately from peer-memory copies; they do not call `cuDeviceCanAccessPeer`, do not pass a foreign device pointer to either backend, and never claim direct DMA. The fallback permits an actual same-process mixed-provider application to be tested even while cross-provider P2P remains fail-closed. CPU doubles validate the control path only; GPU use still requires the authorized mixed-device host/VM configuration.

## R580-to-R595 UVM payload adapters (compiled, not loaded; 2026-10-23)

The composite frontend keeps the R595 standard UVM entry points, but R580 private provider functions now use explicit R580 payload types at the four discovered version boundaries. Module-version CRCs establish provider symbol resolution only; they do not prove that the pointed-to C structures have matching layout or meaning.

- `GetP2PCaps`: R580's payload is 64 bytes and R595's is 72 bytes. R595 inserted `PCIE_BAR1` into `UVM_LINK_TYPE`, shifting NVLink/C2C numeric values. The adapter remaps every known link value, classifies R580 PCIe as `PCIE_BAR1` when either BAR1 size is nonzero, rejects contradictory/unknown values, and defaults the unavailable PCIe-atomics flags to false.
- `QueryCopyEnginesCaps`: both layouts are 8 bytes and `cePceMask` remains at offset 4. R595 added the `scrub` capability bit; the adapter copies R580's known bits and sets `scrub=false`.
- `RetainChannel`: R580 is 1,120 bytes and R595 is 1,128 bytes. The old `pRunlistPRIBaseRegister` and the new `workSubmissionOffset` occupy the same byte offset but are not the same value. The adapter follows the pinned R580 UVM source: doorbell pointer is runlist base plus `0x90`, token is channel ID masked to `CHID[11:0]`, and the shifted SMC fields are copied by name. The 1,120-byte provider buffer resides in the heap-owned request object, not kernel stack.
- `GetPmaObject`: R580 exposes a live 48-byte six-counter prefix; R595 appends three arrays and totals 96 bytes. The pinned R595 runtime reads only `numFreePages64k` and `numFreePages2m`, at offsets 8 and 16, so the live R580 pointer remains valid for those reads. R580 does not provide the appended localized-region counters.
- `RegisterUvmEvents`: the event-table symbol and payload changed. The pinned R595 Linux table is 40 bytes/five callbacks with `isrTopHalf` first; R580 expects 56 bytes/seven callbacks in a different order. The adapter remaps by field and leaves removed `startDevice`/`stopDevice` callbacks NULL. The paired unregister API maps to the renamed R580 entry point and carries no payload.

`tools/audit_hybrid_uvm_abi.py` compiles probes against both pinned header trees and runs payload and callback-table conversion fixtures with UBSan. [Audit v2](../evidence/hybrid-uvm-branch-abi-audit-v2-20261023.json) records exact layouts and input hashes. Frontend build report v10 classifies all 76 standard UVM APIs: six explicitly adapted, five fail closed without provider calls, and 65 whose complete pointee layouts/semantics remain unaudited. The rebuilt module compiles against Linux `7.0.0-38-generic` with objtool active; it has not been installed or loaded, and no hybrid RM or GPU code ran. The missing R595 Volta HAL and RM execution path remain outside this increment.

Historical status recorded 2026-10-21 UTC: same-version R580 proprietary+Open backends were then the leading implementation candidate. That decision was superseded on 2026-10-29 by the R595.99.02 frontend/UVM plus R580.196.07 private Volta provider prototype described below. Neither route has been installed or loaded; hybrid CUDA remains unimplemented and unvalidated.

## R580 UVM module pair and dual-provider requirement

The pinned Open R580.178.04 source plus its separately built, return-thunk-enabled Open RM core now builds `nvidia.ko` and `nvidia-uvm.ko` together for Linux7.0.0-38. The [pair audit](../evidence/r580-uvm-clean-thunk-pair-v1-20261021.json) records76 UVM imports and76 `nvidia` exports with an exact name-set match; module version, dependency and vermagic also match. A separate renamed private Open provider, built from that same R580.178.04 source, now compiles as `hybrid580_open.ko` with 139 namespaced exports and 435 kernel-resolved imports. Its [build report](../evidence/private-open580-native-v3-20261023.json) and isolated source diff establish wrapper compilation, not GPU or RM viability. A deliberate static negative control substituted this provider into the R595.99.02 UVM/frontend closure: it found five cross-version UVM APIs absent from R580 (`AccessBitsBufAlloc/Free`, `AccessBitsDump`, and the two `UvmEvents` functions) and four CRC mismatches (`GetP2PCaps`, `GetPmaObject`, `QueryCopyEnginesCaps`, `RetainChannel`). The [closure report](../evidence/r595-uvm-with-open580-provider-gap-v1-20261023.json) is static module ABI evidence only. Source inspection shows the R580 event names map to a differently sized callback/ops table, while AccessBits has no R580 equivalent; do not stub those operations or assume event-layout equivalence. This does not reject Architecture C: it rejects mixing the R595 UVM interface with an R580 backend without a proven adapter. The same-version R580 frontend/UVM/provider closure and callback field mapping remain to be built and audited.

The first UVM-specific candidate is [patch `0001`](../patches/r580.178.04/uvm/0001-suspend-drain-non-replayable-faults.patch). It drains batches already present in the RM-fed UVM client CPU queue (`shadowBufferAddress`) after suspending the UVM ISR top half and flushing its bottom-half queue, under the existing per-GPU service lock, then flushes the kill-channel queue. This client queue is distinct from the GPU hardware fault buffer and the Hopper confidential-compute indexed shadow path. The candidate does not query RM pending status or rescan after the queue drain. The three-tree [static audit v15](../evidence/uvm-callback-pm-lifecycle-v15-20261021.json), SHA-256 `1bed242182e1c5b6fb829165ba4678aa8be8b8e7746870156a292a381938ac27`, finds no call to the RM service API before ISR suspension in pristine Open, patched Open, or proprietary R580.

The expanded [R580 fault-service audit v9](../evidence/r580-fault-interrupt-service-v9-20261021.json), SHA-256 `862b692b840af9e67aa99d1fdb352ddf56f257289fb8da735a96b0e31fb8e4f9`, maps `0x20801702` to `NV2080_CTRL_CMD_MC_SERVICE_INTERRUPTS`: UVM requests all engines, RM checks pending stall engines, and the GMMU service path consumes the RM-owned software shadow queue and notifies clients. The audit pins 19 source files, 39 static predicates, and auditor SHA-256 `c44f5aa5fc2bf2ca3585ecd3c8572e1e4bf4b58cd75f4fb110f90739085559d9`; its C lexer handles trigraph replacement, line splicing, CRLF/bare-CR line endings, comments, and macro-directive rejection. The generated HAL source assigns the GV100 copier inside the VF RM-variant branch when the T234D/T264D chip-HAL mask condition is false; this conditional source assignment does not establish a particular runtime GPU selection. In the GV100 copier, the empty path rewrites the cached GET pointer and exits without shadow publication. For the nonempty path, client faults are published to the CPU queue before packets are cleared, `fatalFaultIntrPending` is set, fences run, and hardware GET advances. Linux `nvidia_isr` invokes RM fault copying before the UVM top-half callback. Normal IRQ registration targets `nvidia_isr`; MSI-X uses a serialization wrapper, but the PM path does not acquire that wrapper's lock. Hibernate/standby changes RM interrupt software state before GPU power entry; the GV100 copy gate blocks a later caller that observes the disabled state, but does not join an ISR that already passed it. The UVM suspend flag and UVM callback share `interrupts_lock`, which does not establish completion of the earlier RM copy. The full preempt → UVM suspend → per-device suspend order applies only to a successful full-depth procfs path: MODESET and UVM depths return earlier, while the Linux PCI callback directly calls per-device `nvidia_suspend`. The service loop may stop on a stuck interrupt while the enclosing method returns `NV_OK`.

The interrupt controls are distinct. `intrSetIntrEn_IMPL` only stores RM software state, as the strict body predicate confirms. In generated `g_intr_nvoc.c`, `intrSetIntrEnInHw_HAL` selects `intrSetIntrEnInHw_GP100` only for the named TU102/TU104/TU106/TU116/TU117 ChipHal values; its default helper in `g_intr_nvoc.h` is a no-op. `osDisableInterrupts()` separately calls `intrSetStall_HAL`; the generated non-Tegra path selects `intrSetStall_TU102`. Later, `gpuStateUnload()` calls `intrStateUnload()`, whose generated non-T234D/T264D branch selects `intrStateUnload_TU102`; that routine clears top and leaf enable registers. These are source observations, not proof that a helper can be moved earlier for GV100: runtime HAL selection, register semantics, ordering against active RM ISR copies, and restore behavior remain unverified. Do not treat the software gate or a generic interrupt-disable helper as an ISR completion barrier.

Generic Linux at upstream commit `028ef9c96e96197026887c0f092424679298aae8` calls `suspend_device_irqs()` during the later DPM noirq phase, after ordinary device callbacks; the IRQ PM helper synchronizes relevant lines. That barrier is later than `nvidia_suspend()` and is not evidence that a previous UVM queue drain excluded subsequent RM copies. The cited commit has not been matched to the exact Ubuntu `7.0.0-38-generic` source running on PC3. This is an unresolved source ordering question, not an observed hardware fault.

The candidate patch still builds and drains the UVM client queue, but it does not add a host-IRQ/RM-handler barrier or rescan after that drain. No source-backed proof yet makes the RM service control safe and complete as a suspend barrier. Keep this patch as a source/build candidate and do not install it until in-flight ISR ordering and runtime fault-drain/error behavior have a discriminating test.

The same-version Open and proprietary R580 wrapper sources contain byte-identical `nv_uvm_interface.c` (`b41c704d…`), and their compiled private modules each expose the76 functions under backend-specific names. That gives the candidate a reusable, matching provider surface, but the stock R580 `nvidia-uvm.ko` expects one standard-name provider and depends on one `nvidia` module.

Source inspection of `uvm_global.c`, `uvm_gpu.c`, and `nv_uvm_interface.c` establishes why a shim is needed. UVM registers one global callback table and creates one RM session at module initialization. It discovers GPUs by UUID, then passes that UUID alongside the session to device creation. RM-created device, address-space, channel, paging-channel, PMA, and fault handles are returned as opaque values; most later functions receive those handles without a UUID. The [source-backed ownership inventory](../evidence/uvm-interface-ownership-r580-v3-20261021.json) covers all76 declarations, exports and observed UVM callsites. It distinguishes typed handles, multiple-object calls, provider-owned `void *` values, `UvmGpuFaultInfo` with an embedded RM device pointer, and `UvmCslContext` with RM-private context/stack pointers. A viable provider therefore needs paired backend sessions, typed ownership for every opaque object, provider-aware teardown, and an explicit policy for calls involving two providers (notably P2P). Separate PCI PMOps do not provide a global barrier; the exact hybrid PM order is recorded below and is still unimplemented.

### Hibernation and system-PM ordering

The [four-tree NVIDIA/Linux PM contract audit](../evidence/nvidia-hibernate-dpm-contract-v2-20261021.json), SHA-256 `d71db0c11a825e5b9ea01566dce1465af4e29265be7da43fdcc36ed0115cdaef`, found that Linux v7.0 routes DPM RECOVER and THAW to NVIDIA's no-op `.thaw`, while RESTORE calls `.restore` and then `nvidia_resume`. The NVIDIA nested `suspend_count` makes a whole-provider procfs suspend before DPM freeze a risky composition: freeze can add a count that the no-op thaw does not remove. This is conditional source evidence, not a failed hardware sleep test.

The PM prototype models a phased DPM consumer rather than doing the UVM transition from the early notifier. The pre-freezer notifier only closes admission. After the process freezer, one aggregate DPM consumer would drain frontend work, preempt channels on both provider lists, and suspend the shared UVM once. Device links from that consumer to every GPU PCI supplier are the pinned Linux v7.0 ordering primitive: the aggregate suspends before its suppliers and resumes after them. The CPU model now maps all pinned DPM event families and tracks matching suspend, hibernation, and restore notifiers; cross-audit v3 compares these routes against Linux `pm_op()` and both private R580 trees. ## Backend file projection v1

Patch0008 defines a private kernel API, not a userspace ABI. A frontend provider registers a versioned operations object with its own module/fops and a nonblocking `get_backing_file(front,ctl)` callback. Registration copies the operations and keeps a key to the original static object. Callback execution holds a registry read lock with IRQs disabled and a temporary module pin. Unregistration takes the write lock, detaches the copy only after readers finish, then frees it outside the lock. No permanent module pin can obstruct the provider's module_exit.

The lock order is files->file_lock, projection registry read lock, then atomic frontend mapping access. The callback may not sleep, call RM/fget, acquire a files table lock or recurse. It returns one reference to a fully opened backend file from a mapping whose lifetime the frontend owns. This requirement matters because `iterate_fd` may hold its files lock. RCU/SRCU was rejected for this shared-boundary design because the inspected kernel exposes the relevant primitives GPL-only; the four new reader/writer lock imports are ordinary exports. This is not proof that the complete Open wrapper can be reused by the proprietary module.

`nv_get_file_private` and `nv_match_dev_state` validate the real backing file's fops, character major/minor, private container and device mapping. Control lookup additionally requires the control object/open flags. Direct control matching preserves prior behavior; frontend matching requires a GPU mapping. Original embedded nvfp/event containers survive and returned references are paired with the original fput path. An FD reference does not isolate concurrent user ioctls; eventual controls must be frontend-owned and unexposed. No provider is installed. Patch0009 supplies an opaque RM invocation adapter, compiled and CPU-modeled below; it has not executed.

The raw-RM experiment retains endpoint.stack across alloc/free. The new versioned session API retains only callback/context and stable ownership tokens; its dispatch does not retain a temporary stack. Raw and opaque calls use the same root transaction/status/quarantine implementation. Different identities are necessary routing invariants, not evidence of independent RM globals. Endpoint copies do not acquire references; the frontend must hold them through cleanup or quarantine teardown and serialize complete transactions.

## Exclusive control-session adapter

Patch0009 allocates a real, unpublished backend control file on the anchor's superblock/mount, preserving the original NVIDIA file-private container and vendor open/close path. Creation uses alloc_anon_inode, fops_get and alloc_file_pseudo with explicit failure unwinding; it never installs a user FD or opens a GPU file. The shared endpoint header is copied verbatim into the wrapper. The endpoint identifies this backend's control object and actual backing file. Two sessions from the same backend therefore cannot masquerade as two independent backends to the broker.

The session owns a kref, an invocation mutex and the immutable file pointer. Callers hold a session reference through each invocation and mapping publication. Each ROOT32/64/FREE call validates exact types and supported null-pointer forms, initializes the correct embedded status to unwritten, then takes the mutex, PM read lock and an independent temporary stack before rm_ioctl. Transport and embedded status remain separate. Calls retain the current caller's credentials; no privileged worker substitutes identity. The open/close stack remains attached to the vendor file.

Final session release performs fput outside the invocation/PM locks. Backing-file references held by projection can extend file lifetime and fput itself can defer release. This API does not certify synchronous RM cleanup. The real frontend must unpublish mappings, drain callers, free confirmed roots or quarantine, and release every reference in order. The legacy adapter and both frontend revisions compile separately below; none has executed in the kernel.

## Backend-owned GPU `.mmap` delegation (compiled, CPU-modeled)

The observed NVIDIA sequence now has a source-backed frontend route. A GPU ioctl carrying the pinned R580 `nv_ioctl_nvos33_parameters_with_fd` packet is forwarded to exactly the backend selected by BDF. The private backend projection maps its embedded frontend fd to that GPU session's genuine backend `struct file`; the native `nv_add_mapping_context_to_file()` stores the RM mapping context on that file. The frontend `.mmap` then obtains a referenced file from the same GPU session, calls the exported Linux `vma_set_file()` during initial VMA setup, invokes that backend file's native `.mmap` callback, and drops its temporary reference. The VMA retains the backend file, so the NVIDIA fault/close callbacks recover the expected backend-private state even if the frontend GPU fd closes first.

This choice follows the actual ownership contract rather than reconstructing NVIDIA's page mappings. Linux v7.0 exports `vma_set_file()` for replacing the initial VMA backing file; the Linux dma-buf mmap path uses the same helper before calling its exporter. The target kernel's `Module.symvers` confirms `vma_set_file` is an ordinary `EXPORT_SYMBOL`.

The frontend transaction mutex serializes this `.mmap` callback with GPU ioctls. It rejects control files, propagates interrupted locking, fails closed if the session/file/mmap callback is unavailable, and leaves mmap-error cleanup to the VFS while the VMA already points at the backend file. `tests/test_hybrid_frontend.py` models the actual `NVOS33+fd` GPU ioctl followed by mmap for both R580 backends, asserts both operations share the same backend file, and tests VMA-held backend lifetime after frontend-fd close, backend mmap failure, control-file rejection and interruption. ## Isolated UVM migration policy for R580

The candidate's isolated execution mode has no cross-provider P2P dependency path. R580 UVM can normally stage an inaccessible source through CPU memory, but one migration transaction then needs ordering from the source GPU to the destination GPU. A simple unlock/wait/retry would restart the whole migration and can repeat the source copy. The current candidate mirrors UVM's staged-page calculation, subtracting pages already available from a directly accessible processor, then returns `NV_ERR_NOT_SUPPORTED` before mapping invalidation or destination chunk population when CPU staging is required. It repeats the check before copy dispatch after allocation-retry boundaries.

This is a safety boundary, not a completed hybrid UVM feature: isolated GPU migrations requiring CPU staging remain unsupported until each asynchronous phase can be committed and revalidated across lock release. Patches [`0010`](../patches/r580.178.04/uvm/0010-reject-unsupported-isolated-staged-migrations.patch), [`0011`](../patches/r580.178.04/uvm/0011-preflight-unsupported-staging-before-unmap.patch), and [`0012`](../patches/r580.178.04/uvm/0012-exact-isolated-staged-page-mask.patch) compile against the exact standard-identity `nvidia` frontend ABI. The candidate has not been loaded; there is no hardware evidence for UVM behavior, concurrent migration safety, or same-process hybrid CUDA.

Directly accessible migration has a separate unresolved owner-transition risk. The isolated push guard returns `NV_ERR_NOT_SUPPORTED` when the block tracker has pending work from another GPU. `uvm_va_block_make_resident_copy()` performs two invalidation batches before destination population/copy, and fault service then proceeds through revoke and map subphases; the inspected path has no wait/retry boundary between them. The unmap batches collect per-GPU pushes and merge them into the block tracker, so a later copy or mapping push can meet a still-pending foreign owner. This is conditional on tracker completion timing: it does not establish that every direct migration fails. The hash-pinned [phase audit](../evidence/r580-uvm-isolated-service-phases-v2-20261028T1933Z.json) records the source chain and all nine checks. Any fix must resume a well-defined phase after dropping the block lock; a whole-function retry that repeats completed GPU-to-CPU staging is unsafe.
